# Herramientas para crear contenido de Rogue Command

**Revisado:** 2026-10-17

**Objetivo:** producir unidades, etapas/mapas y AI originales para el mod Rogue Evolution. El loader se mantiene como infraestructura necesaria.

**Estado de evidencia:** a la fecha, ningún contenido de este repositorio está confirmado en una partida de Rogue Command. Compilar el loader, validar manifests y abrir AssetBundles fuera del juego no demuestra que una unidad nueva se registre y aparezca, que una etapa produzca un mapa jugable ni que una AI ejecute una decisión. Los ejemplos siguen siendo hipótesis de integración hasta observar esas acciones durante una sesión iniciada por Steam.

## Resultado de la búsqueda de skills

No encontré una skill pública específica para crear contenido de Rogue Command ni para desarrollar su cargador. Sí encontré `bepinex-mono-modding`, una guía comunitaria de BepInEx 5/Mono, y una guía para IL2CPP. La segunda no se aplica a este juego. La primera cubre patching y diagnóstico general, pero se enfoca en trainers y menús; además, ordena cambiar `BepInEx.cfg` para fijar `HideManagerGameObject=true` antes de discriminar la causa. Ese diagnóstico no está validado para este juego y las pruebas históricas de clon no atribuyeron el bloqueo al loader; no instalé ni apliqué la guía. Sus instrucciones de cambiar la instalación/perfil del juego directamente también se apartan del requisito local de arrancar Rogue Command por Steam. La skill comunitaria de `bepinex-mcp` se centra en inspeccionar y modificar un juego que ya está ejecutándose; no crea modelos, mapas o datos de juego.

La documentación oficial de BepInEx y HarmonyX sirve para el trabajo de plugin y Harmony. La búsqueda en el catálogo curado de `skill-installer` tampoco encontró una skill de creación de mods de Unity Mono que encaje con el contenido de este repositorio. Se mantienen como guía principal la documentación de este repo, `reverse-engineer-anything` para evidencia de binarios y `engineering:code-review` para revisar cambios; no se instaló una skill de otro backend como sustituto.

Preparar Runtime Unity Editor con `tools/Setup-BackendTools.ps1 -RuntimeUnityEditor`. El script comprueba el SHA-256, extrae solo el subdirectorio del plugin a `.tools/` y no instala nada en Rogue Command, no cambia su configuración y no inicia el juego.

Preparar UnityDataTool con `tools/Setup-UnityDataTool.ps1`. El script descarga la release oficial fijada en v2.4.0, comprueba el digest SHA-256 publicado por GitHub, valida las rutas del ZIP y deja el CLI y sus dependencias en `.tools/UnityDataTool-2.4.0/`. El CLI no se copia al juego ni modifica archivos de proyecto. Ejemplos desde la raíz del repo:

```powershell
& .\.tools\UnityDataTool-2.4.0\UnityDataTool.exe archive list content\packs\sample-native-expansion\bundles\sample-native-expansion.bundle
& .\.tools\UnityDataTool-2.4.0\UnityDataTool.exe sf objectlist content\packs\sample-native-expansion\bundles\sample-native-expansion.bundle -f json
```

La instalación local reportó `2.4.0+ea5a7d6eb0869d376f9a65bdc7da22d618257ea1`; `archive list` encontró un SerializedFile y `sf objectlist` devolvió objetos de tipos `GameObject`, `Mesh`, `MeshRenderer` y `MeshFilter`. Es inspección offline del bundle distribuible, no una prueba del cargador o del comportamiento runtime. Unity publica UnityDataTool como CLI de análisis de archivos de juego y AssetBundles; su soporte no cambia el requisito de construir estos bundles con la versión exacta de Unity del juego.

Para el backend, BepInEx 5 Mono y HarmonyX ya están presentes como referencias de compilación. No se requiere una segunda capa de patches. Mantener `RuntimeOverlayUi` como diagnóstico del loader y usar el inspector externo para confirmar objetos y estado nativos en runtime; son funciones distintas.

Las copias locales se pueden preparar de nuevo con `tools/Setup-ContentAuthoringTools.ps1 -Blender -UnityExplorer`. El script fija las versiones, verifica SHA-256 antes de extraer y deja los programas bajo `.tools/`; no cambia la instalación del juego ni lo inicia. BepInEx y BepInEx MCP ya están instalados en la carpeta de Rogue Command de Steam; UnityExplorer sigue sin desplegarse y el bridge MCP aún no se ha confirmado en una partida.

La herramienta runtime solo cuenta como apoyo a una prueba. La evidencia de aceptación debe atribuirse a Rogue Command ejecutado desde Steam y mostrar el recorrido completo: unidad registrada, elegible en el pool y creada; etapa incorporada a la progresión y mapa generado; AI seleccionada y decisión propia ejecutada. Una captura del overlay, un `BepInEx` “plugin loaded”, un `AssetBundle.LoadFromFile` exitoso o la presencia de un GameObject aislado no bastan por sí solos.

## Recomendaciones de uso

1. **Unidad:** empezar desde una plantilla nativa compatible para conservar la lógica de gameplay y crear una silueta original en Blender o con geometría de Unity. Importar el modelo a `unity/RogueCommandAssetAuthoring/`, compilarlo como AssetBundle Windows x64 y asignarlo a una ruta visual nativa validada. La ruta de overlay actual conserva los componentes nativos, pero no reasigna rigs o animaciones. Una nueva apariencia puede probarse en Editor; el control de movimiento, armas, sombras/materiales y renderizado se confirma dentro del juego. Si llega a escena, observar la jerarquía y los componentes con Runtime Unity Editor.
2. **Etapa y mapa:** la variante de etapa actual clona `StageParametersScriptableObject` y reutiliza mundo y blueprint pools del juego. Esto es útil para probar progresión y balance, pero no crea por sí mismo un mapa original. Un mapa nuevo necesita las referencias serializadas completas de mundo, generador y pools que el juego espera; investigar y construir ese grafo forma parte del contenido, no se resuelve añadiendo campos numéricos al loader.
3. **AI:** los paquetes eligen módulos compilados por ID; no distribuyen DLLs. `sample:scheduled-base-build` amplía producción nativa; `sample:reactive-base-defense` añade una decisión táctica acotada: detecta unidades del jugador con ataque habilitado que atacan un edificio AI y envía hasta cuatro defensores móviles con ataque y movimiento habilitados, al punto en que detectó la amenaza. Solo utiliza unidades con orden `DoNothing` o `Move`, limita radio/cooldown/respuestas y deja que el juego reanude el movimiento guardado tras la orden posicional. El paquete `sample-reactive-ai` proporciona una etapa de plantilla y perfil nativo para probarlo. La implementación y el manifest pasan validación local; todavía falta observar el comportamiento en una partida iniciada por Steam.
4. **Validación:** hacer preflight del pack, inspeccionar el AssetBundle con Unity Editor/UnityPy/UnityDataTool y registrar hashes. Estos son checks offline. La aceptación requiere una ejecución reversible del juego **a través de Steam**, confirmando que la unidad se instancia y aparece en el pool, la etapa genera el mapa previsto y la AI ejecuta la nueva decisión. Runtime Unity Editor ofrece una vista adicional del runtime, pero su presencia no cuenta por sí sola como prueba de integración.

## Herramientas que no añaden valor ahora

- **Addressables:** el mod ya entrega bundles y el loader usa `AssetBundle` directamente. Addressables es una capa superior que genera catálogos, direcciones y flujo de dependencias; todavía no hay evidencia de que el juego tenga un catálogo Addressables utilizable por packs externos. No añadir esa dependencia sin una necesidad demostrada.
- **Asset Bundle Browser:** Unity lo describe como herramienta auxiliar/pre-release y de alcance básico. El repo ya tiene `RogueCommandAssetBundleBuilder.cs`, que aplica las rutas y límites del pack; usar el builder existente da una salida más controlable.
- **Habilidades BepInEx IL2CPP:** no aplicar sus instrucciones al juego Mono ni mover el plugin a BepInEx 6/Il2CppInterop sin que cambie y se verifique la identidad técnica del juego.
- **Herramientas de runtime:** BepInEx 5.4.23.5 Mono x64 y BepInEx MCP están instalados en la carpeta Steam; se verificó una sesión iniciada por Steam y se observaron capacidades y jerarquía mediante llamadas MCP de solo lectura. Runtime Unity Editor 6.3.2.1 y UnityExplorer siguen solo en `.tools/`; desplegar como máximo uno por prueba reversible. Empezar con observación de solo lectura porque las herramientas ofrecen superficies que pueden cambiar estado o ejecutar código. Para retirar la instalación del bridge, usar `.tools/BepInExMCP/deployment/Restore-BepInExMcpDeployment.ps1`, que mueve solo los archivos instalados con hash intacto y deja intactos los modificados o adicionales.
